# 数字水印与鲁棒性评测

用 Python 实现两种图像数字水印，然后**攻击自己**，看哪种能扛住。

- **LSB（最低有效位）**：把信息藏进像素最低位，肉眼完全看不出，但一压就没了
- **DCT（离散余弦变换）**：藏在频率域的中频系数上，配合重复编码和打散，抗攻击能力强得多

**一句话结论**：LSB 在 10 种攻击下只扛住 1 种；DCT 扛住 9 种。

---

## 一、什么是数字水印

在图片里藏一段看不见的信息（比如版权归属、生成来源、用户 ID），
需要的时候能提取出来。

它有三个互相矛盾的目标：

| 目标 | 含义 |
|---|---|
| **不可见性** | 藏了之后图片看不出来被改过 |
| **鲁棒性** | 图片被压缩、裁剪、转发之后，水印还在 |
| **容量** | 能藏多少信息 |

**三者不可能同时最优。** 改得越多越抗攻击，但也越容易看出来——
这就是这个项目要展示的核心矛盾。

---

## 二、两种方法

### LSB：把信息藏进最低位

每个像素值是 0-255，把最后一位（最低位）改掉，值只变 ±1，人眼绝对看不出来。

```
原值 10110101 = 181
改成 10110100 = 180   ← 只差 1，肉眼看不出
        ↑
     这一位藏我们的数据
```

**优点**：简单，容量极大（一张 512×512 图能藏 78 万比特）
**致命缺点**：任何一次 JPEG 压缩都会重写最低位，水印直接消失

### DCT：藏在频率域

把图切成 8×8 小块（和 JPEG 一样），对每块做离散余弦变换转到频率域，
然后做**配对比较**：

```
要藏 1 → 让系数A比系数B大 delta
要藏 0 → 让系数B比系数A大 delta
```

提取时只需比较 A 和 B 谁大。

**三个关键设计**：

1. **藏在 Y（亮度）通道** —— JPEG 对色度的压缩比亮度狠得多
2. **藏在偏中频的位置** —— 低频改动容易被看出来，高频容易被 JPEG 量化掉
3. **重复编码 + 打散 + 多数表决** —— 每个比特藏 20 份，散布到整张图，提取时投票

## 三、怎么运行

```bash
python app.py              # 交互程序（推荐先试这个）
python experiment.py       # 命令行跑完整实验
```

### 交互程序 `app.py`

用 **Tkinter**（Python 自带，无需安装）。把整条链路做成可手动操作的界面：

```
① 水印设置     选图片 → 输入要藏的信息 → 选方法（DCT / LSB）→ 点「嵌入水印」
② 施加攻击     拖动滑块：JPEG 质量 / 裁剪 / 高斯噪声 / 缩放 / 亮度
③ 检测结果     实时显示提取结果、投票一致率、攻击后 PSNR
```

**拖动滑块时水印会在眼前"死掉"**——把 JPEG 质量从 100 往下拖，
到某一档结果会从「✅ 抵御成功」变成「❌ 水印已被破坏」，
那个临界点就是这种方法的能力边界。

工作分辨率限制在 512～800 像素之间（太小则放大、太大则缩小），
**和命令行实验用同一套规则，保证两边结果可比**。

### 命令行

```bash
python experiment.py                     # 用自动生成的测试图
python experiment.py --image 你的照片.jpg  # 用自己的照片
python experiment.py --message "你的学号"  # 换一段要藏的信息
python experiment.py --delta 30          # 调整嵌入强度
```

**单独嵌入 / 提取**：

```bash
python watermark.py embed   --method dct --image 照片.jpg --message "秘密"
python watermark.py extract --method dct --image 照片_含水印.png
```

**依赖**：只需要 `numpy` 和 `opencv-python`，纯 CPU，不需要显卡。

## 四、实验结果

以**合肥工业大学校徽**为测试图（294×294，程序自动放大到 588×588），
嵌入信息 `HFUT-CS-2025`，DCT 参数 delta=25、重复 20 次。

### 不可见性

| 方案 | PSNR | 说明 |
|---|---|---|
| LSB | **90.96 dB** | 改动 ±1，放大 40 倍看差异图也几乎全黑 |
| DCT | **41.39 dB** | 40 dB 以上即肉眼不可辨 |

### 鲁棒性

| 攻击方式 | LSB | DCT |
|---|---|---|
| 无攻击 | 成功 | 成功 |
| JPEG 压缩 q=90 | 失败 | **成功** |
| JPEG 压缩 q=70 | 失败 | **成功** |
| JPEG 压缩 q=50 | 失败 | 失败 |
| JPEG 压缩 q=30 | 失败 | 失败 |
| 缩放 50% | 失败 | **成功** |
| 高斯噪声 σ=3 | 失败 | **成功** |
| 高斯噪声 σ=8 | 失败 | **成功** |
| 裁剪边缘 64px | 失败 | **成功** |
| 亮度 +15 | 失败 | **成功** |
| **合计** | **1/10** | **8/10** |

### 结论

1. **两种方法都做到了不可见**（PSNR 均 ≥ 40 dB）。运行 `experiment.py` 后打开 `output/5_总览对比.png`，
   可以看到三张图肉眼无差别，而放大 40 倍的差异图揭示了水印藏在哪里。
2. **LSB 完全不抗攻击**。一次 JPEG 压缩就摧毁它，只适合"图片绝不会被改动"的场景。
3. **DCT 抗噪声、抗缩放、抗裁剪**，代价是容量小（每块 1 比特）且需要调参。
4. **JPEG 压缩是主要威胁**：q=50 时中频系数开始被量化掉，q=30 时彻底失效。

### ⭐ 一个额外的发现：图片类型决定水印难度

同一套代码，换一张图结果就不一样：

| 测试图 | 低纹理块占比 | DCT 抗住攻击 |
|---|---|---|
| 合成风景图（纹理丰富） | 少量 | **9/10** |
| **校徽**（大面积纯色 + 细线条） | **49%** | **8/10** |

**为什么校徽更难？** DCT 水印靠"把信息藏进中频纹理"。
校徽有一半的块是纯白背景，**没有纹理可供隐藏**——改动只能落在平坦区域上，
相对更显眼，压缩时也更容易被抹掉。

这个规律可以推广：**照片 > 插画 > 图标/线稿**，纹理越少越难做鲁棒水印。

程序会自动统计低纹理块占比并写进 `实验结果.md`。

## 五、开发中踩的五个坑 ⭐

### 坑 5：交互程序和命令行跑出来的结果对不上

**现象**：做好交互程序后，同样是校徽、同样嵌 `hfut-se-2025`，
程序里显示**重复编码 6 次**，而命令行实验里是 **20 次**，抗攻击能力差一大截。

**原因**：命令行实验里有一句"图片太小就放大到短边 512"的处理，
校徽只有 294×294，放大后 8×8 分块从 1296 涨到 4096，重复次数才能到 20。
**交互程序里我没写这一步**，直接用了原尺寸。

**修法**：把同一套分辨率规则搬到程序里，并在状态栏显示
「原图偏小，已放大至 512×512」，让用户知道程序做了什么。

> **教训**：同一条算法有**两个入口**（命令行、界面）时，
> 只要预处理逻辑有一处不同，结果就会不一致——
> 而且这种不一致**不报错、不崩溃**，只是数字悄悄变了。
> 凡是多入口的项目，**预处理规则必须收敛到同一个函数里**。

这部分是这个项目里最有价值的内容——**每个坑都对应一个真实的原理**。

### 坑 1：DCT 水印"没被攻击也提取失败"

**现象**：嵌入后立刻提取，得到的是乱码。

**排查**：嵌入端用了 9 次重复（1152 个块），而提取端按"填满所有块"推算，
认为是 32 次（4096 个块）。**多出来的 2944 个未修改的块参与了投票，把真实结果冲掉了。**

**根因**：嵌入端和提取端对"重复了多少次"的理解不一致。

**教训**：任何"两端约定"的参数，必须有一方可靠地告诉另一方，或者双方能按同样的规则算出来。
我最后改成"自动用满所有块"，两端由图片尺寸算出同一个值，问题消失。

### 坑 2：裁剪攻击下 16 个比特"全军覆没"

**现象**：加上裁剪攻击后，水印完全提取不出来。但按说只裁掉边缘，中间的信息应该还在。

**排查**：推导了一下块序号和比特序号的对应关系。当时用的是顺序平铺——
第 k 个比特放进第 k 个块。结果承载同一个比特的所有块满足：

```
块序号 ≡ 比特序号 (mod 载荷长度L)
```

而 L 恰好是 64 的倍数（因为块数是 64 的倍数），所以**这些块全部落在同一列上**。
裁剪掉左边 8 列，就有 16 个比特的所有副本被一次性摧毁，投票也救不回来。

**根因**：平铺方式让"同一比特的副本"在空间上高度相关，损坏不独立。

**修法**：用固定随机种子生成一个置换，把副本**打散**到整张图的各个位置。
这样损坏被摊薄到所有比特上，不再集中打击少数几个。

### 坑 3：裁剪能提取了，但仍有比特出错

**现象**：打散之后裁剪攻击改善不明显，仍失败。

**排查**：裁剪攻击是用灰色填充被裁掉的区域。而**灰色块的 DCT 系数全是 0**，
于是判断式 `d[P1] > d[P2]` 恒为假（0 不大于 0），这些块**永远投 0 票**。

**这不是随机噪声，是系统性偏差。** 重复 20 次也压不住——
只要某个比特的多数副本落在被裁区域，它就必然被判成 0。

**修法**：提取时先检测"死块"（块内标准差接近 0 = 平坦区域 = 已被破坏），
把它们标记为无效，**不参与投票**。只统计有效票的多数。

**修完后，裁剪 64px 成功提取。**

> **坑 2 和坑 3 的区别值得记住**：
> 坑 2 是"损坏分布不均"，坑 3 是"损坏有方向性"。
> 前者靠打散解决，后者只能靠识别并剔除坏数据。
> **重复/冗余只能对抗随机误差，对抗不了系统性偏差。**

### 坑 4：换成校徽后，阈值把"好块"误杀了

**现象**：用纹理丰富的合成图时一切正常；换成校徽后，成绩明显变差。

**排查**：校徽有 **49% 的块是纯白背景**。这些块在**嵌入水印之前**方差是 0，
看起来就像"死块"。但嵌入之后，DCT 系数被改动，它们的方差升到 **1.16** 左右——
**刚好卡在原来的死块阈值 1.0 之上，只有 16% 的余量。**

一旦经过 JPEG 压缩，平滑效应会把这些块的方差压到 1.0 以下，
于是它们被误判成"死块"、排除出投票——**好数据被当成坏数据扔掉了。**

**修法**：把阈值降到 0.5。

**为什么 0.5 是安全的**：

| 块的类型 | 方差 |
|---|---|
| 真死块（被灰色填充） | **精确为 0** |
| 水印化后的纯色块 | **≥ 1.16** |

两类样本之间有充足的分隔空间，取中间偏下的 0.5 最稳妥。

**教训**：**判据阈值不能拍脑袋定，要看两类样本的实际分布。**
我最初设 1.0 只是觉得"听起来合理"，从没检查过真实数据的取值范围——
**凭直觉设的阈值，往往恰好卡在最危险的位置上。**

## 六、文件说明

| 文件 | 作用 |
|---|---|
| `watermark.py` | 核心：LSB 和 DCT 的嵌入 / 提取 |
| `attacks.py` | 10 种攻击（JPEG、缩放、噪声、裁剪、亮度） |

**换一张图重跑全部产出**：

```bash
python experiment.py --image 你的图.png   # 跑实验，更新 output/ 和 实验结果.md
python compare_types.py                   # 生成"图片类型对比"的材料（报告第六节要用）
python make_report.py                     # 更新 Word 报告
python make_poster.py                     # 更新成果汇总图
```

> `compare_types.py` 会额外跑一遍合成风景图作为对照，
> 产出对比图与数据（写入 `output/` 目录）。
> 如果跳过这步，报告第六节会自动降级为只有本次测试图，不会引用不存在的数据。

## 七、已知局限

1. **提取要求图片尺寸不变**。裁剪攻击是"裁掉边缘后贴回原位"模拟的，
   如果图片真的被裁小，8×8 分块网格会错位，提取会失败。
   实际系统会用同步码或模板来解决，本项目未实现。
2. **嵌入强度是固定的**。对纹理丰富的图片（AC 系数本来就大），
   固定 delta 可能造成可见变化。更好的做法是按块内容自适应调整。
3. **容量很小**。512×512 图只能藏 21 字节，因为每块只承载 1 比特且要重复 20 遍。
4. **只测了图像**。音频、视频水印（以及王垚飞老师方向里的"生成式隐写"）未涉及。
